# canine-vi-diacritics

A small, fully reproducible fine-tune with a before/after measurement: **restoring Vietnamese diacritics** (text with all marks stripped in, correct text out)
with **CANINE-s** (Google, about 0.13B parameters; the Hugging Face card shows 0.1B, F32 weights 528 MB, Apache-2.0), fine-tuned on Vietnamese Wikipedia sentences. One command runs setup, data, training, evaluation
and writes `results.md` and `results.json`. By Grawwww, MIT licence for our code.

| Test set, 5,000 held-out sentences | Syllable accuracy | Letter accuracy | Whole sentence right |
|---|---|---|---|
| Copy the input (no diacritics) | 18.93 % | 74.05 % | 0.00 % |
| Baseline: most frequent form of each syllable seen in training | 76.41 % | 93.09 % | 4.44 % |
| CANINE-s before fine-tuning (random head) | 5.58 % | 55.32 % | 0.00 % |
| **CANINE-s fine-tuned (this repo)** | **94.61 %** (95 % CI 94.41-94.83) | **98.41 %** | **47.96 %** |

Compute: 3 epochs on 400,000 sentences = 18,750 steps in 19.5 min on one RTX 4090 (peak 4.72 GB VRAM allocated); 0.34 GPU-hours for train + eval.
Estimated rental cost for that GPU time: about $0.11 (Community) to $0.30 (Secure) at RunPod's list prices (page read 2026-10-16, page marked as updated 2026-10-08). An estimate, not an invoice.
Every number above comes from `results.json` / `results.md`.

**Why Vietnamese and not Arabic.** The standard Arabic diacritization corpus, Tashkeela, is GPL-2.0, and its re-uploads labelled MIT or Apache-2.0 are of
unverified provenance (we did not check) (details in [licences.md](licences.md)). The task is the same shape (restore marks on letters), so we used a corpus whose licence
we could read at the source. **Nothing here has been run on Arabic.**

## How it works

- Input: the sentence with every diacritic removed (`đ` becomes `d`). Output: one label per input character = the combining marks that character
  should carry (36 labels, including "none"). The text is rebuilt by composing each input character with its predicted marks, so the model **cannot
  change a base letter**; an assertion checks this on every test sentence (0 changes). Impossible combinations (a tone mark on `b`) fall back to the plain letter.
- Model: `google/canine-s` (character-level, no tokenizer vocabulary) with a token-classification head, pinned to revision `75d6d0b3f4d0bffed0ca7ddd0b73949977d4ca02`.
- Training: AdamW (weight decay 0.01, gradient clipping 1.0), lr 5e-5, linear warm-up (5 %) and decay, batch 64, bf16 autocast, 3 epochs, seed 1234. No hyper-parameter search; the number of
  epochs was chosen from the validation curve of an earlier 1-epoch run (`results/prelim_1epoch_train_log.jsonl`, validation 91.0 % at the end).

## Data and split (no leakage)

Source: Vietnamese Wikipedia, 2023-11-01 dump as published by Wikimedia on Hugging Face (`wikimedia/wikipedia`, revision `b04c8d1ceb2f5cd4588862100d08de323dccfbaa`,
first of four parquet shards, 322,170 articles). Sentences are kept if they are 40-200 characters, NFC, use only Latin letters, digits and basic punctuation,
have at least 5 diacritised letters, and have at least 70 % letters.

- The split is **by article**: SHA-1 of the title mod 100 gives test (0-4), validation (5-7), train (the rest). Splits are a function of the title, so they are disjoint by construction; train/test disjointness is asserted in the code.
- Exact duplicate sentences are removed, and any train sentence that also appears in validation or test is dropped (asserted: zero overlap with test).
- Used: 400,000 train sentences (99,174 articles), 2,000 validation, 5,000 test (2,314 articles). The unigram baseline's lookup table is built from train only.
- Counts are in `results/data_stats.json`, file hashes in `results/data_sha256.txt`. The 5,000 test sentences are not committed (share-alike text, see licences); they are regenerated by `./run.sh`.

## Metrics

Syllable accuracy = share of whitespace-separated tokens (punctuation stripped) that match the original exactly. Letter accuracy counts every
alphabetic character, including the many that carry no mark, which is why "copy the input" is not zero. Sentence accuracy = whole sentence identical.
Confidence intervals: sentence-level bootstrap, 1000 resamples.

## Run it

Needs Linux, an NVIDIA GPU (we used a 24 GB RTX 4090; training peaks near 5 GB, so smaller cards should work but we did not test), `uv`, bash, about 0.8 GB of model and data files from Hugging Face, plus the Python packages (about 5.6 GB installed in `.venv`).

```bash
./run.sh
```

It creates `.venv` (Python 3.12, versions pinned in `requirements.txt`), downloads the data shard and model, builds the splits (about 14 min CPU), trains
(about 20 min), evaluates and writes `results.md`, `results.json` and `results/`. Set `GPU_WRAP="<command>"` to wrap the two GPU steps in a lock or scheduler on a
shared GPU. The final weights (about 0.5 GB) are written to `work/model` (git-ignored; we deleted ours, `./run.sh` regenerates them).

## Reproducibility check

We ran the whole pipeline twice from the same pinned environment, the second time rebuilding the splits from the cached download. The three data files were
**byte-identical** (sha256 match). The model results were **not** bit-identical, because GPU kernels are not run in deterministic mode: fine-tuned syllable accuracy
94.58 % (first run, `results/run1_eval.json`) vs 94.61 % (second run, reported above). The baselines are identical. Expect differences of a few hundredths of a point between reruns.

## What did not work, and what we did not measure

- **Sentence-level success is modest.** Under half of the test sentences (47.96 %) come out exactly right; 5.4 % of syllables are wrong, so a typical 22-syllable sentence (110,862 syllables over 5,000 sentences) has about one error.
- **Ambiguity the model cannot resolve from a sentence.** The most frequent errors (`results/top_errors.json`) are valid-word swaps: `loại`/`loài`, `từ`/`tự`, `con`/`còn`,
  `cùng`/`cũng`, `quan`/`quân`, `cổ`/`có`. Some are genuinely ambiguous without wider context, and the model sees one sentence at a time.
- **Spelling conventions are label noise.** Wikipedia mixes `hoá`/`hóa` and `Hoà`/`Hòa` (tone mark placement). The model can only guess which style an article uses; these count as errors here.
- **Names and foreign words**: names such as `Binnya U` or `Oberkommando` pass through unchanged (no marks to restore), and the rare Sino-Vietnamese names are often wrong. See the "model wrong" examples in `results.md`; they are the first 8 of a seeded shuffle, not selected.
- The "before fine-tuning" row is a randomly initialised head on the pretrained encoder. It shows that the task is not solved by the pretrained model alone, but it is not a strong baseline; the unigram lookup is the meaningful one.
- Mistakes made on the way (from the author's notes; no logs of these failed runs were kept, except the 1-epoch run in `results/prelim_1epoch_*`): the first training attempt crashed in validation because an impossible mark combination changed the string length (the base-letter assertion caught it; fixed as described above);
  the first evaluation crashed because a torch 2.14 native Triton kernel needed a C compiler (`TORCH_DISABLE_NATIVE_JIT=1` is now set in `run.sh`); in the first full run `make_results.py` failed on a malformed number in `timing.json` (a shell arithmetic formatting bug, fixed in `run.sh`) and the file was corrected by hand for that run only. The reported run's `timing.json` was written by the fixed script.
- **Not measured**: variance across training seeds (one seed per run, two runs total); other learning rates or batch sizes; larger models or more data (validation still rose slowly at the end, 94.94 % to 95.21 % over the last 3,000 steps); text outside Wikipedia (news, chat, OCR); sentences longer than 200 characters; comparison with published Vietnamese systems (our split and filtering differ, so numbers are not comparable); CPU inference speed; any language other than Vietnamese. The test sentences are filtered to ones with at least 5 diacritised letters, so scores on text with few marks may differ.
- Peak VRAM is the PyTorch allocator peak of our process on a card shared with other jobs; GPU time is wall time of the train and eval steps including model loading.
